# videolab — agent context

Tooling that turns a running app into a demo video. This repo is the **engine and
the template**; it holds no per-app content and tracks nothing about any project.

- **Record**: Playwright drives the real running app and saves footage.
- **Compose**: Remotion adds intro, outro, zooms, and captions to that footage.

The model writes and runs code. It never generates video pixels.

## The core rule: fork-on-create

A video never renders the tracked template. When a video is created — explicitly
with `videolab new <video>`, or automatically the first time `record`, `studio`,
or `compose` touches it — the template is **copied** into the project folder.
From then on that copy is the video's own code:

- **Edit the project's copy freely.** Any style, motion, layout, or structure
  change for one video goes in `projects/<app>/<video>/studio/src/`. It cannot
  affect any other video.
- **The template may evolve.** `studio/` (tracked) is the starting point for
  *future* videos only. Changing it never affects existing videos, because they
  run their own copy. There is no automatic sync: adopting a template
  improvement into an old video is a manual, deliberate copy of specific files.
- **`bin/` and `lib/` are the shared engine** (recording, normalization,
  orchestration). They run for every video, so engine changes do affect all
  videos — keep them generic and stable.

## Layout

```
bin/videolab.js                  CLI entry: list | new <video> | record | studio | compose
lib/                             engine: recorder, composer, scaffold, app/path helpers
studio/src/                      tracked Remotion TEMPLATE — copied into new videos,
                                 never rendered directly by any video
projects/                        scratch state, gitignored, deletable
projects/<app>/<video>/
  flow.js                        Playwright script (default export)
  video.json                     beats: title, timings, zooms, captions (see below)
  studio/src/                    this video's OWN copy of the template — its look
                                 and motion live here; edit freely
  raw/footage.webm               generated by record, disposable
  render/                        generated: normalized MP4, props.json, entry.tsx
  out/<video>.mp4                generated by compose, the final video
  .snapshots/                    saved state zips (see "Snapshots" below)
```

`<app>` comes from the `name` field in the app's `demo.yml`. `.gitignore` excludes
`projects/` wholesale. It can be deleted at any time; recreating a video
re-forks from the current template.

## Working directions (bidirectional)

Videolab reads the app repo and writes only into itself. Either side can start:

- **From the app repo** ("make a video of this app"): the primary contract. Run
  the CLI with the app repo as the working directory.
- **From videolab** ("go to this folder, there's a project there — run it and
  make a video"): run the same commands from videolab and pass
  `--cwd <app-repo>` so `demo.yml` is found, e.g.
  `node <videolab>/bin/videolab.js record tour --cwd C:/path/to/app-repo`.
  Equivalently, set the per-command working directory to the app repo. Either
  way the app repo is only ever **read**: footage, scaffolds and renders land
  in `projects/` here. Do not permanently move the session into the app repo.
- **`videolab list`** adapts: with a `demo.yml` in the working directory it
  lists that app's videos; without one it lists every app's videos
  (`app/video`), so it works from videolab itself.

## Contract for agents working from an app repo

The app repo (the one with `demo.yml`) stays clean — videolab never writes into it.
Run the CLI from the app repo (or pass `--cwd <app-repo>` from anywhere):

```
node <videolab>/bin/videolab.js list
node <videolab>/bin/videolab.js new <video>
node <videolab>/bin/videolab.js record <video>
node <videolab>/bin/videolab.js studio <video>
node <videolab>/bin/videolab.js compose <video>
```

**May edit (per video):** `projects/<app>/<video>/flow.js`,
`projects/<app>/<video>/video.json`, and everything under
`projects/<app>/<video>/studio/src/` — that last one is the video's own
composition code, and per-video design belongs there.

**Never edit:** the tracked `studio/` to serve one video (it is the template for
future videos — that is a tool change and needs an explicit request), `bin/`,
`lib/`, another app's `projects/` folder, or any `raw/`, `render/`, `out/`
directory.

**Fonts.** A system family (`Arial`, `Georgia`, `Verdana`) is a plain string in
`video.json` or in a style's `fontFamily`. A Google Font needs `loadFont()`:
register it in the **project's** `studio/src/fonts.ts` copy for one video, or in
the **template's** `fonts.ts` only when the request is a deliberate template
change. Components never call `loadFont()` directly.

## Where an edit belongs

- **Beats** (when things happen): `video.json`. Title, subtitle, tagline, `fps`,
  `intro`, `outro` seconds, `zooms`, `captions`, `cursor`, `width`/`height`.
  This is the cheap, low-risk, live-preview edit surface — prefer it.
- **Looks** (colors, fonts, sizes): the style keys `captionStyle`,
  `introStyle`, `outroStyle` in `video.json` still work with the default
  template's components.
- **Anything JSON can't express** (different layout, new animation, extra
  scenes, a renamed composition id): the project's own `studio/src/`. It owns
  its code; it may diverge from the template in any way.

When the user asks to save or restore a video's state ("take a snapshot", "go
back to the baseline"), use the **Snapshots** section below — exact commands,
do not improvise a different format.

### Canvas and props panel

- **Previewing a video** (`videolab studio <video>`): the canvas inspector edits
  land in that project's `studio/src` — that is fine and expected, it is the
  video's own code. The props panel shows `video.json` values live but never
  writes files ("Cannot update computed prop" means "this is not saved"): read
  where the user lands and translate it into `video.json` (beats/styles) or the
  project's components.
- **Developing the template** (`npm run studio` at the repo root, placeholder
  props): edits land in tracked `studio/src`. Deliberate template changes only.
  Before any task, and always before `compose`, check `git status` and
  `git diff studio/` for tracked-template changes you did not make yourself;
  never keep accidentals silently — show the user the diff and ask.
- `video.json` remains the source of truth for beats; the project's code is the
  source of truth for everything else in that video.

## Preview before composing

`studio` prepares `render/footage.mp4` and `render/props.json` and opens Remotion
Studio with the video's real footage and edit. It does not render:

```
node <videolab>/bin/videolab.js studio <video>
```

- The final video is produced only by `compose`. Do not render before the user has
  approved the preview.
- The command watches `video.json` and `raw/footage.webm`. Saving an edit rewrites
  `render/props.json`, and Studio picks it up live — no restart needed. Changes to
  the project's own `.tsx` files hot-reload through Studio's bundler.
- Studio shows a real props panel (sliders/no-drag number fields/colour pickers)
  built from the project's `studio/src/schema.ts`.
- Port defaults to 3000 and falls back to the next free port. Tell the user the URL.
- The server runs from the videolab root, but invoke the command from the app repo
  (or with `--cwd <app-repo>`).
- The command keeps running until stopped (Ctrl+C). Run it in the background so the
  agent can keep editing while the user reviews.

## video.json

Times are seconds relative to the recording; `intro` and `outro` are seconds too.

- `title`, `subtitle`, `tagline`: intro and outro text.
- `fps` (default 30), `intro` (default 3), `outro` (default 4).
- `cursor` (default false): draw a pointer and click ripples in the recording. Read by
  `record`, not `compose`. Headless Chromium does not show the real mouse pointer.
- `zooms`: keys `{at, scale, originX?, originY?}`. `at` must strictly increase.
  `originX`/`originY` are percentages of the frame and set where the zoom focuses.
  Transitions ease in and out.
- `captions`: `{from, duration, text}`.
- `width`/`height` (optional): output window dimensions in pixels. Default to the
  recorded footage dimensions (no crop). Set them smaller than the footage (e.g.
  `720`×`1280` over a `1280`×`800` desktop recording) to render a vertical slice of
  a desktop page that pans/zooms within the footage.
- `captionStyle`, `introStyle`, `outroStyle` (optional): style overrides merged over
  the component defaults. Keys include `background`, `color`, `fontFamily`,
  `fontSize`, `fontWeight`, `border`, `borderRadius`, `boxShadow`, `transform`,
  `padding` (caption); `background`, `titleColor`, `titleFontSize`, `subtitleColor`,
  `subtitleFontSize`, `fontWeight` (intro); `background`, `taglineColor`,
  `taglineFontSize`, `titleColor`, `titleFontSize`, `fontWeight` (outro). Honored by
  the default template's components; a forked project decides for itself.
- `composition` (optional): the Remotion composition id to render. Default `"Demo"`;
  useful when a forked project registers a differently-named composition.

## Recording pitfalls

- The app must not already respond at `demo.url`; videolab never kills servers it did
  not start.
- Dev servers that compile API functions on first hit (e.g. `vercel dev`) can stall the
  first real request. Warm those endpoints off-screen in `flow.js` via
  `page.request.get(...)`, which never touches the DOM and never appears in footage.
- Remotion occasionally times out on one frame (`delayRender`). Re-run `compose`.

## Snapshots — save and restore a video's state

A snapshot freezes the whole video folder into a zip so the user can undo a bad
iteration deterministically. Because the folder now contains the video's own
composition code, a snapshot reproduces the exact rendered behavior too. Snapshots
live in `projects/<app>/<video>/.snapshots/` — plain zips plus a `manifest.json`
that records a label and optional comment for each. No git, no tooling.
They are never committed (already covered by the `projects/` rule) and are
ignored by `record`/`studio`/`compose`. Use these exact PowerShell commands;
do not improvise a different restore procedure.

### Save a snapshot

Run when the user says "take a snapshot", "I like this, save it", or similar.
`<short-label>` is a slug describing the state, e.g. `step5-baseline`. If the
user gives a comment ("this is the version with the new zooms"), record it in
`comment`; otherwise use an empty string. The zip plus the `manifest.json`
entry are what the user later reads to identify snapshots:

```powershell
$dir  = "<videolab>\projects\<app>\<video>"
$name = "{0:yyyy-MM-dd_HHmm}_{1}" -f (Get-Date), "<short-label>"
New-Item -ItemType Directory -Force -Path "$dir\.snapshots" | Out-Null
Get-ChildItem -LiteralPath $dir -Exclude ".snapshots" |
  Compress-Archive -DestinationPath "$dir\.snapshots\$name.zip" -Force
$manifest = "$dir\.snapshots\manifest.json"
if (Test-Path $manifest) { $all = @(Get-Content $manifest -Raw | ConvertFrom-Json) }
else { $all = @() }
$all += [pscustomobject]([ordered]@{
  name    = "$name.zip"
  savedAt = (Get-Date -Format o)
  comment = "<optional comment from the user>"
})
$all | ConvertTo-Json -Depth 4 | Set-Content $manifest -Encoding UTF8
```

Everything inside the video folder except `.snapshots/` is included — `flow.js`,
`video.json`, `studio/`, `raw/`, `render/`, `out/` — so a restore reproduces the
exact state, code, footage and rendered video included. Tell the user the
snapshot name.

### List snapshots

Read `manifest.json` (it survives restores — restore never touches
`.snapshots/`). Fall back to plain listing if it is missing:

```powershell
$snaps = "<videolab>\projects\<app>\<video>\.snapshots"
if (Test-Path "$snaps\manifest.json") {
  Get-Content "$snaps\manifest.json" -Raw | ConvertFrom-Json |
    Select-Object name, savedAt, comment
} else {
  Get-ChildItem $snaps -Filter "*.zip" | Select-Object Name, LastWriteTime
}
```

### Restore a snapshot — DESTRUCTIVE, always confirm first

Restore replaces the entire video folder with the snapshot's contents. Always:

1. List the snapshots and ask the user to confirm the exact zip to restore.
2. (Recommended) Save a safety snapshot of the current state first, labeled
   `pre-restore`, using the Save recipe above.
3. Run the restore, then tell the user it is done.

```powershell
$dir = "<videolab>\projects\<app>\<video>"
$zip = "$dir\.snapshots\<timestamp>_<short-label>.zip"
$tmp = New-Item -ItemType Directory -Path (Join-Path $env:TEMP ([guid]::NewGuid().ToString()))
Expand-Archive -Path $zip -DestinationPath $tmp.FullName -Force
Get-ChildItem -LiteralPath $dir -Exclude ".snapshots" -Force |
  Remove-Item -Recurse -Force
Copy-Item (Join-Path $tmp.FullName "*") $dir -Recurse -Force
Remove-Item $tmp.FullName -Recurse -Force
```

The delete step (removing everything except `.snapshots/`) is essential: it
removes files created *after* the snapshot, which is what makes restore exact
instead of a merge. Restore is all-or-nothing — never restore individual files
"partially". After a restore, `raw/`, `render/` and the project's `studio/` copy
come back as they were, so re-running `record`/`compose` is only needed to
produce *new* footage or edits.

## Hard rules

- Never fake app behavior. Demo footage must come from the real UI. Zooms, captions,
  intro, and outro are fine; replaying one take as if it were several, or any
  simulated result, is not.
- Preview before composing: run `studio`, iterate until the user approves, and only
  then run `compose`.
- Nothing under `projects/` is ever committed except `projects/README.md`, and no
  video, footage, or app-specific file belongs anywhere else in this repo.
- Per-video design lives in that video's own `studio/src` copy — never in the
  tracked template, and never in `bin/`/`lib/`.
- Do not write anything into the app repo.
- Do not install storylab/stickman tooling here.
- No shared `node_modules` between videolab and target apps. (Project copies inside
  videolab resolve `remotion`/`react` from videolab's own `node_modules` by Node's
  upward walk — no per-project install is needed.)
